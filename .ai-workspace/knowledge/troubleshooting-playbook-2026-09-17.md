# 排查与优化方法论（实战复盘版）

> 来源：2026-09-16 ~ 09-17 的真实工作（715 看不到 3D 点云、镜像带开发地图、固件 1.0.16 发布）。
> 每个方法都配了**这次的具体做法**和**踩过的坑**，不是泛泛而谈。

---

## 第一部分：六条核心原则

### 原则 1：先怀疑"题面"，再怀疑系统

用户给的描述里往往混着**观察**和**推断**。推断部分要先验证，否则会把排查引到错的方向。

- **案例**：题面是"715 少了 `/livox/lidar/pointcloud` 这条话题，所以 WEB/APP 看不到 3D 点云"。
  前半句是观察（真的），后半句是推断（错的）。我先做的不是查那条话题，而是查**前端到底订阅哪个话题**——
  一行代码 `frontend/src/ros/topics.ts:14` 就否掉了整个推断。
- **做法**：把题面拆成 `观察` / `推断` 两栏，先花 5 分钟验推断。验证成本通常极低（读一行代码、跑一条命令），
  但方向错了要赔上几小时。

### 原则 2：先划清"责任域"，再动手

同一个现象可能来自客户端、服务端、网络、配置、数据、镜像。**先确定"谁负责这一段"**，可以立刻砍掉大半搜索空间。

- **案例**：715 的问题在"客户端（APP/WEB）→ rosbridge → ROS 话题 → 驱动"这条链上。
  我先确认**数据是有的**（`/global_cloud_navigation` 10.5Hz、13k 点），于是责任域从"设备没数据"切到"订阅/传输"。
- **做法**：画一条最小链路，逐段标"已确认/未确认"。**只对未确认的段落动手**。

### 原则 3：一定要有"可测量的判据"，不要靠感觉

"看不到点云"不是判据；"订阅后 10 秒内收到 ≥1 条 binary 消息"才是。

- **案例**：我写了一个 30 行的 websocket 探针（`repro_ws_probe.py`），把"看不看得见"变成
  `messages=N` 这个数字，后面所有判断都建立在这个数字上。
- **做法**：动手前先写下**通过/不通过**各是什么数字或什么日志行。做不到就说明还没理解问题。

### 原则 4：分层二分，每次只切一半

链路是分层的（客户端 / 传输 / 服务端 / 数据源），每次切掉一半，用最便宜的手段测中间那一段。

- **案例**：客户端探针（我的 PC）订阅 → 能收到（cbor-raw 26 条）；换成 `cbor` → 0 条。
  **一条命令就把问题锁在"服务端对 cbor 的处理"**，与 APP、前端、浏览器全都无关。
- **做法**：优先用"绕过客户端"的手段（curl / rostopic / 自己的小脚本），把客户端因素一次性排除。

### 原则 5：对照法（A/B）——找一台"好的"机器

同样的镜像、同样的客户端，只有一台出问题，**两台之间的差异就是答案**。

- **案例**：701 正常、715 异常。于是：
  1. 同一探针、同一参数分别打两台 → 715 被拒、701 正常（现象可复现）；
  2. 两台日志计数对比：701 该错误 **0** 条、715 十几条（现象有唯一性）；
  3. **整棵 rosbridge 包逐文件 sha256 对比** → 只有 3 个文件不同（定位到文件）；
  4. 逐文件 diff → 一行（定位到行）。
- **做法**：对照要**同口径**：同一命令、同一参数、同一时刻的同类状态（注意别在建图态和导航态之间比）。

### 原则 6：结论必须可回滚、可复现、可交接

排查结论要能让别人照着重放。做不到就说明证据不够。

- **案例**：最后交付的是「探针脚本 + 设备侧取证脚本 + 原始日志 + 逐字时间戳」，
  任何人能在 2 分钟内复现"被拒"，也能在修好后复现"通过"。
- **做法**：把命令、参数、时间戳、文件路径写进结论里；贴**原文**而不是"我看到了错误"。

## 第二部分：手法工具箱（怎么用、什么时候用）

### 2.1 客户端探针（自己写最小复现）

**什么时候用**：怀疑"客户端 ↔ 服务端"这一段，但客户端不可控（APK、浏览器、别人的程序）。

**怎么做**：用最笨的协议客户端复刻客户端的行为（同样的订阅报文、同样的压缩方式），只打印"收到几条/多大"。
```python
ws.send(json.dumps({"op":"subscribe","id":"probe","topic":T,
                    "type":"sensor_msgs/PointCloud2","compression":C,
                    "queue_length":1}))
# 只统计：文本回执（服务端报错会以 status 回）、二进制消息条数与字节数
```
**这次的收获**：
- `cbor-raw` 能收到、`cbor` 收不到 → 服务端路径差异；
- 服务端**未必**会把拒绝回给客户端（这次的 `already established with type *` 只写进了服务端日志），
  所以探针必须配合服务端日志看，不能只看客户端有没有报错。

**陷阱**：探针本身会改变系统状态（我那个 `--no-type` 模式会把话题锁成通配）。**先想清楚探针会不会污染现场**，
会污染的就只在实验机上用，并在结论里注明。

### 2.2 全树指纹对比（比"读代码"快十倍）

**什么时候用**：两台机器行为不同，怀疑代码/配置漂移。

**怎么做**：对目录下所有文件算 sha256，列表比对，**先缩小到文件，再 diff 文件内容**。
```bash
find $DIR -name '*.py' | sort | while read f; do printf '%s %s\n' "$(sha256sum "$f"|cut -c1-16)" "$f"; done
```
**这次的收获**：`rosbridge_library` + `rosbridge_server` 共 56 个 .py，只有 3 个不同；
我一开始只比了 5 个"看起来相关"的文件，**漏掉了真正的元凶**（`capabilities/subscribe.py`）。
补做全树对比后，一行代码定位了根因。

**教训**：**不要按"相关性"挑文件比**。全量指纹很便宜（几百个文件几秒钟），挑着比最容易漏。

### 2.3 日志锚点对齐（用时间戳把两个视角缝起来）

**什么时候用**：两个视角（客户端日志 / 服务端日志）各自都"看起来正常"。

**怎么做**：找**同一秒**的两侧记录，做因果对应。
**这次的收获**：
```
客户端(APP logcat)  20:01:27.781  Point-cloud subscribe (cbor-raw, …): /global_cloud_navigation
服务端(rosbridge)   20:01:27.498  [Client 2] Subscribed to /global_cloud_navigation
服务端              20:02:42.273  [ERROR] … already established with type *   ← 我的探针被拒
```
三行一比，"谁先注册、谁被拒"就无可辩驳了。

### 2.4 用"外部真值"验证（别相信二手结论）

**什么时候用**：文档/注释/别人的结论说"这个仓库是公开的/这个脚本能用"。

**怎么做**：用与结论无关的通道亲自验一次。
- 判断镜像能否匿名拉：**用 docker 自己的流程**（`docker manifest inspect`），而不是 curl registry API
  （ACR 匿名 API 会 401，但 docker 能拉——我曾据此误判"仓库私有"）。
- 判断脚本能不能下载：从**另一台机器**匿名 curl，并顺手 `bash -n` 语法检查 + 检查行尾（CRLF 会让设备上执行失败）。

### 2.5 状态机与重启顺序（设备类问题必查）

**什么时候用**：容器化 ROS 系统里"某个功能突然没了"。

**这次的关键事实**：
- `core` 容器里 rosbridge 的 launch **没有 `respawn`** → `pkill` 后不会自愈（我踩过：一度把 9090 弄停）；
- **master 重启后，其它容器里的 ROS 节点必须重启**，否则 `/clock` 不来、业务报"ROS 时间未就绪"；
  正确顺序：`core` → 导航容器 → `firmware-sensors`；
- 判断"数据源活着吗"用 `/clock` 频率 + 话题**发布者**（`rostopic info` 看 Publishers），而不是 `rostopic hz`
  （容器内可能加载不了自定义消息类型，`hz` 会假死）。

### 2.6 证据归档（把"我查过"变成"你可以重放"）

**怎么做**：原始日志（含时间戳）+ 采集命令 + 一条"判读规则"。
```bash
# 采集（只读）
docker exec core bash -c 'L=$(ls -t /root/.ros/log/*/rosbridge_websocket-*.log|head -1); \
  grep -c "already established with type" "$L"; grep -c AnyMsg "$L"'
```
**判读规则示例**：这三项计数**都应为 0**；>0 说明有客户端订阅姿势不对。

## 第三部分：三个完整案例复盘

### 案例 A：715 的 3D 点云看不到（含我的一次误判）

| 步骤 | 动作 | 得到什么 |
|---|---|---|
| 1 | 怀疑题面：查前端订阅哪个话题 | `/global_cloud_navigation`，与 livox 无关 → 否掉原始推断 |
| 2 | 确认数据侧 | 该话题 10.5Hz、13k 点、订阅者就是 rosbridge → 数据没问题 |
| 3 | 客户端探针分层 | `cbor-raw` 收到 / `cbor` 收不到 → 锁定服务端 |
| 4 | 对照 701 | 701 的 `cbor` 正常（37 条/12s）→ 差异在设备侧 |
| 5 | 全树指纹对比 | 56 个 .py 里只有 3 个不同 → 缩小到文件 |
| 6 | 逐文件 diff | `subscribe.py` 一行：`if compression == "cbor-raw": msg_type = "__AnyMsg"` |
| 7 | 因果验证 | 该行让 cbor-raw 订阅（APP 的做法）无条件把话题锁成通配 → WEB 被拒、APP 也拿不到可解析数据 |
| 8 | 修在正确的层 | 补丁入源码 + 写进 Dockerfile → 真编译 → 发镜像（而不是手工改容器） |
| 9 | 验收判据 | 日志三项计数为 0 + 探针 cbor 能持续收到 |

**我在第 5 步之前犯的错**：只比了 5 个"看起来相关"的文件，于是把原因猜成"APP 订阅不带 type"，
还写了份指向 APP 开发的交付包。**全树对比后才发现真凶是服务端一行代码。**
→ 教训：**"相关性挑选"是排查里最危险的偷懒**；能用全量指纹就不要挑。

### 案例 B："APP 里一堆地图名"（先分清"数据"还是"代码"）

- 直觉猜测：数据库被拷进镜像了。
- 验证：镜像里 `find -name nav_api.db` → **没有**；只有 `schema.sql`。
- 再查：镜像里 `install/share/my_nav/maps/api_map/` 有 322 个开发地图文件；
  读代码 `database.py:_bootstrap_installed_maps(seed_installed=True)` → 首次建库时把镜像自带地图**播种**进 DB。
- 结论：不是 DB 进镜像，是**镜像自带地图被播种**。修法也就不同了（清镜像里的地图 + 保留空目录占位）。

**方法要点**：现象（APP 里有地图名）离原因（镜像自带文件 + 首启播种逻辑）隔了两层，
**先证伪最贵的假设（DB 进镜像），再顺着代码找真正的机制**。

### 案例 C：发布固件 1.0.16（"不覆盖已有版本"的工程做法）

| 步骤 | 动作 |
|---|---|
| 1 | **先盘库存**：`docker manifest inspect` 逐个确认 ACR 上已有 tag（`latest`/`runtime-base`/`compile`/`1.1`）与各自 config |
| 2 | **先问版本号的来源**：`compile.bash` 在编译期 `sed` 注入 `Major/Minor/Patch`（不是 STM32 的号，STM32 走 `stm32_iap.py` 按文件名解析）→ 下一版 = 1.0.16 |
| 3 | **保全将被移动的指针**：推送前把旧 `latest` 的内容打成新 tag `rollback-pre-keyframe-20260831-102133` 推上去 |
| 4 | 推新 tag（`1.0.16`）→ 再推 `latest` |
| 5 | **远端校验**：`docker manifest inspect` 比对 manifest/config digest，确认 `1.0.16` 的 config == 本地镜像 ID；旧内容仍可按 rollback tag 拉到 |
| 6 | 源码入库（补丁文件 + Dockerfile 补丁层 + 版本号），推云端 |

**要点**：**"更新"和"覆盖"的区别在于有没有留下旧指针**。任何时候要移动一个共享 tag（`latest`、`stable`），
先给它当前内容起一个永久名字，再移动。

## 第四部分：我犯过的错，以及纠正流程

| 错误 | 后果 | 纠正动作 | 沉淀下来的规则 |
|---|---|---|---|
| 把镜像里的 7 张**开发地图**拷进设备、让 DB 改指设备路径（自以为是"保护现场数据"） | 等于把开发垃圾永久留在生产设备上 | 删文件 + 删 7 条 DB 行 + 删我建的备份，设备回到 27 套真实地图 | **镜像里带的东西＝垃圾**；不确定时先问"这东西该不该存在"，而不是"怎么保住它" |
| 只比 5 个文件就断定"APP 订阅不带 type"，还写了交付包 | 交付包结论错误，差点让 APP 开发白改代码 | 全树指纹对比 → 找到真凶；更正交付包与 known-issue，并显式标注"原判作废" | **结论要标证据强度**；"看起来相关"不等于"已证实" |
| 手工 `pkill` 了没有 respawn 的 rosbridge | 9090 一度中断 | 按正确顺序重启 core → nav → firmware-sensors | 动服务前先确认**它由谁托管、有没有 respawn** |
| 用 `FROM sha256:<本地镜像ID>` 构建 | BuildKit 当成远端镜像名，构建失败 | 改成给本地镜像起名 + 传统 builder | 构建报错先看**它把参数理解成了什么** |

**纠正流程（我现在的做法）**：
1. 先止损（回滚错误动作，恢复服务）；
2. 把新证据和新结论写进同一份文档，**保留"原判断 → 为什么错 → 现在的判断"**，不要偷偷改掉；
3. 主动告诉相关人"上一版结论作废"，并说明**新结论要他们做什么**（这次是"APP 不用改，改固件"）。

## 第五部分：优化思路（从"能跑"到"跑得好"）

### 5.1 优化前必须先量

优化 = 在约束下改一个可测指标。**没有基线数字的优化都是猜。**

- 反例（这次的相机问题）："三路高清导致延迟" → 必须先量出：每路 **分辨率 / 帧率 / 编码 / 实测 Mb/s**，
  以及"延迟"到底是多少毫秒、在哪一段产生的（采集？传输？APP 渲染？）。
- 量什么（模板）：
  | 指标 | 怎么量 | 目标 |
  |---|---|---|
  | 帧率 | `rostopic hz`（注意容器内消息类型加载问题） | ≥30fps |
  | 带宽 | `rostopic bw`（序列化字节/秒 ×8 → Mb/s） | 越低越好，先定预算 |
  | 端到端延迟 | 客户端打点（收到帧的时间戳 vs 帧内时间戳） | 先测出基线 |
  | 画质 | 主观 + 分辨率/质量参数 | 可接受即可 |

### 5.2 分清"症状级修"和"根因级修"

- **症状级**（这次 APP 端限流）：客户端少收几帧 → 延迟缓解，但**带宽占用没变**，且每接一个新客户端都要重做一遍。
- **根因级**（应当做的）：在**产生帧的地方**用合适的编码（OAK 芯片自带 H.264/H.265 硬件编码）→
  30fps 也能把码率压到原来的百分之几，且所有客户端同时受益。
  > ⚠️ **现状修正（2026-09-17 深夜）**：上面这个「OAK 硬编 H.264/H.265」**已被实测否决** ——
  > OAK 同时最多 5 个视频编码器，而三路相机各要占一个 MJPEG 供 `/keyframe`（**空间重建的输入，不可牺牲**），
  > 剩下只有 2 个余量给视频链路；且自适应切档复杂度高、弱网下会丢关键帧。
  > **实际采用的根因级做法是「导航侧 MJPEG 重编码」**（`capture.py`，压缩强度 50%、分辨率恒定不降、带画质地板）。
  > 详见 `.ai-workspace/handoff/MJPEG-VIDEO-LINK-TUNE-50PCT-HANDOFF-2026-09-17.md`。
  > 「在产生帧的地方编码」这个**思路**仍然成立，但**落地方式不是 OAK 硬编**，别再照这条去实现 H.264。
- 判断标准：**这个改动会不会让"下一个新客户端/新设备"自动受益**。会 → 根因级；不会 → 症状级。

### 5.3 改在"正确的层"

同一件事有三个可改的层，选择影响可维护性：

| 层 | 例子 | 特点 |
|---|---|---|
| 运行时（手工改容器内文件） | 2026-08-19 那两个 rosbridge 补丁 | 见效快、**不可复现**、容器重建即丢 → 只能当应急 |
| 镜像层 | 补丁写进 Dockerfile | 可复现、可分发；需要发版 |
| 源码层 | 补丁文件入库 + 构建期断言 | 可审计、可回归；**首选** |

**这次的正确做法**：三层都做了一遍，但最终落点是**源码 + Dockerfile 断言**，
并在构建期加"缺文件/缺关键行就构建失败"的断言，防止再次漂移。

### 5.4 优化方案要带"边界与回退"

任何优化交付都要回答：**怎么验证、怎么回退、影响谁**。
（这次发布：验收判据三条、回退 tag 一个、影响面 = 只有新拉镜像的设备。）

### 5.5 把"猜"变成"实验清单"

对相机这个还没开始的优化，我建议的推进顺序：
1. 量基线（三路分辨率/帧率/编码/Mb/s/延迟）；
2. 回答"10fps 锁死 vs 导航 20fps"——**先证伪**：是同一路流被重复渲染？还是导航另有一条编码链路？
   还是触发源（10Hz 硬同步）与编码帧率本来就解耦？（用实测数据回答，不要推理）
3. 列出可选方案（OAK 硬编 H.264 / JPEG 参数调优 / 抽帧 / 换传输通道），每个方案给出**预期码率与画质代价**；
4. 选一个做小实验（一台设备、一路相机），量出结果再推广。

## 第六部分：可复用清单（照抄使用）

### 排查启动清单
```
[ ] 把题面拆成"观察"和"推断"，先验推断
[ ] 画最小链路，标注每段 已确认/未确认
[ ] 写下"通过/不通过"的判据（数字或日志行）
[ ] 找一台"好的"机器做对照（同口径）
[ ] 用绕过客户端的手段先切一半链路
[ ] 需要比较代码/配置时：全树指纹 → 缩小到文件 → 再 diff
[ ] 结论要含：命令、参数、时间戳、原文日志、文件路径
[ ] 会污染现场的探针，标注清楚并只在实验机用
```

### 发布（改共享资源）前清单
```
[ ] 先盘库存：现有 tag/版本/各自 digest
[ ] 确认版本号从哪来、下一版是多少（别猜）
[ ] 要移动共享 tag（latest 等）前：先给旧内容起永久名字并推送
[ ] 只推新 tag，不动无关 tag
[ ] 远端校验：manifest/config digest == 本地构建产物
[ ] 写清验收判据 + 回退命令
[ ] 源码/构建脚本同步入库（否则镜像不可复现）
```

### 交接清单
```
[ ] 设备清单（名称 ↔ IP ↔ 角色），SSH 命令模板，sudo/凭据说明
[ ] 已完成项 + 证据路径（日志、摘要、digest）
[ ] 未决项 + 每项的"下一步动作 + 判据"
[ ] 踩坑清单（含"看着像 A 其实是 B"的误导项）
[ ] 关键路径速查表（源码树、取证目录、事实源、文档）
```

## 附：一句话总结

**排查的本质是"用最便宜的手段，把不确定性砍半"**：先验推断 → 划责任域 → 定判据 → 分层二分 → 对照全量指纹 → 收敛到一行 → 修在正确的层 → 留下可重放的证据。
**优化的本质是"先量再改，改在根因，改在源码，留好回退"**。
