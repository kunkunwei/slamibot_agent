三、非交互环境安装（Cursor/自动化场景）
若无法手动选 fishros 菜单，按以下顺序执行：

PASS='设备sudo密码'
# 1. 基础依赖
echo "$PASS" | sudo -S apt update
echo "$PASS" | sudo -S apt install -y python3-pip python3-yaml
# 2. 装 Docker（fishros 选项 8）
cat > /tmp/fish_docker_config.yaml << 'EOF'
chooses:
- choose: 8
  desc: 'Docker'
EOF
echo "$PASS" | sudo -S bash -c '
  export FISH_INSTALL_CONFIG=/tmp/fish_docker_config.yaml
  export FISHROS_URL=http://mirror.fishros.com/install/
  mkdir -p /tmp/fishinstall/tools/translation/assets
  wget -q $FISHROS_URL/install.py -O /tmp/fishinstall/install.py
  cd /tmp/fishinstall && python3 install.py
'
# 3. 装 ROS Noetic（apt 直装最稳）
echo "$PASS" | sudo -S DEBIAN_FRONTEND=noninteractive apt-get install -y ros-noetic-desktop-full
# 4. 跑完整配置脚本（跳过 Docker/ROS，执行后续步骤）
curl -fsSL https://gitee.com/electech6/d360_deploy/raw/master/setup_env.bash -o /tmp/setup_env.bash
echo "$PASS" | sudo -S bash /tmp/setup_env.bash
注意： 必须以 root 跑 fishros，否则内部 sudo 会失败：

echo "$PASS" | sudo -S bash /tmp/setup_env.bash   # 正确

五、雷达网口配置（必须单独做）
雷达走 eth0，配置文件中主机 IP 为 192.168.1.55。

# 配置 eth0 静态 IP（NetworkManager，开机自动生效）
sudo nmcli connection modify "有线连接 1" \
  ipv4.method manual \
  ipv4.addresses 192.168.1.55/24 \
  ipv4.never-default yes \
  ipv6.method ignore \
  connection.autoconnect yes
sudo nmcli connection up "有线连接 1"
雷达 IP 修正（重要）
默认配置 /etc/slamibot/MID360_config.json 中雷达 IP 为 192.168.1.181，
实际设备可能是 192.168.1.105，需 ping 确认后修改：

ping -c 2 192.168.1.105    # 通则改配置
ping -c 2 192.168.1.181    # 不通则不用
# 若实际是 .105，修改配置：
sudo sed -i 's/"ip" : "192.168.1.181"/"ip" : "192.168.1.105"/' \
  /etc/slamibot/MID360_config.json
重启传感器服务
sudo docker restart core firmware-sensors

12.2 一键安装（推荐）
------------------------------------------------------------------------

  # 取脚本（2D 导航=可选组件；来源 gitee.com/electech6/d360_deploy → nav2d/install_2d_nav.sh）
  curl -fsSL -o /tmp/install_2d_nav.sh \

脚本做的事：
  - 检查 docker / docker compose v2 / compose 文件存在 / core 是否在跑
  - 检查传感器前置：/clock 有频率、/livox/lidar 有发布者、/dev/shm/timeshare 的数值在持续变化
    （冻结时只告警不中止，但导航/建图/相机时间戳会不可用）
  - 拉取镜像；往 /etc/slamibot/system/docker-compose.yml 写入 scout-nav 服务（改前自动备份）
  - docker compose up -d scout-nav；等 /health 返回 200；超时自动回滚 compose 并重建旧服务
  - 只在 core/firmware-sensors/ota_web 之外新增一个服务，不动其它容器、不删镜像、不 prune、不删数据

12.3 手动等价操作（拿不到脚本时照这段做）
------------------------------------------------------------------------
sudo mkdir -p /var/lib/slamibot/scout-nav

在 /etc/slamibot/system/docker-compose.yml 的 services: 下追加：

  scout-nav:
    image: registry.cn-shanghai.aliyuncs.com/slamibot/d360_nav2d:1.2.5
    container_name: scout-nav
    network_mode: host
    privileged: true
    shm_size: 64m
    restart: unless-stopped
    volumes:
      - /var/lib/slamibot/scout-nav:/var/lib/slamibot/scout-nav
    depends_on:
      - core

sudo docker compose -f /etc/slamibot/system/docker-compose.yml up -d scout-nav

说明：不需要任何环境变量；不要覆盖 entrypoint/cmd；host 网络下不需要 -p
     （80 WEB / 5000 API / 9090+19090 rosbridge 直接对外）。

12.5 已踩过的坑（现场必读）
------------------------------------------------------------------------
- 到点语音播报依赖讯飞网关（127.0.0.1:5011）。**自 2026-09-18 起该网关由语音容器 `voice-assistant` 提供**
  （不再装在宿主上，见第十三章）；未部署语音容器时新句子不会出声
  （日志 `TTS gateway failed with no PCM available`）。
  兜底做法：把参考设备数据根里的 `db/tts_cache` 一并拷过来——缓存命中即播，不依赖网关也不等云端。
- 相机（OAK）与雷达要分开看：`/livox/lidar` 有数据 ≠ 相机出图。相机不出图时先看 OAK 驱动节点是否真在跑。
- timeshare 冻结时不要启动相机：相机会持续发布完全相同的 header.stamp（硬件同步失效）。
  先修雷达点云链，再让相机起来。timeshare 在宿主 /dev/shm，容器重启不清、整机重启才清。
- 日志里的 `Can not get index` / `Storage point data failed` 来自 bag 存储路径，
  点云正常时也会刷，**是长期噪声，不代表雷达故障**；真故障判据是 `/livox/lidar` 没有发布者
  （用 `rosnode info /livox_lidar_publisher2` 看 Publications）。
- 到点语音播报：1.2.1 起为"任务开始前预热 + 到点读缓存"，不再依赖云端；
  若云端网关不通也不会再出现等十几秒才出声的情况。（网关现由语音容器提供，见第十三章。）
- 建图模式依赖 `install/share/fast_lio_gravity_align/{launch,config}`，
  缺失时建图会启动失败；镜像构建已加防呆（缺资源直接构建失败）。
- 语音链路（run_mic / assistant_runtime / 讯飞网关）**不在导航镜像里**，现在由**独立的语音容器**
  `voice-assistant` + 宿主单元 `slamibot-audio-node-sync.service` 承载，属独立部署项（第十三章）。
  **不要**再按旧文档在宿主上用 crontab 拉 run_mic_sherpa——容器版会与宿主版抢麦克风和 5011 端口。
- 容器数据全部在宿主 /var/lib/slamibot/scout-nav；换镜像或重建容器不丢。
  迁移到另一台设备：tar 这个目录搬过去即可（含数据库、地图、相册、TTS 缓存、FAST-LIO PCD）。

====================================================================
十四、图传链路静态 IP（基础装机第 5 步已自动做；现场只做复核）
====================================================================

背景：D360 有三条链路 —— **热点、WiFi、图传**。图传（遥控器/APP 数传）要求本机在对应网口上有
      **192.168.144.87/24**，该地址由 **NetworkManager 档案**提供（APP 里「改 IP」改的就是档案里的地址）。

⚠ 踩过的坑（现场最费时间的一条）：
  档案用 `connection.interface-name` **硬绑网卡名**，而**网卡名因机型/枚举顺序而异**
  —— 701 是 eth2、715 是 eth1。715 上**两份档案都没有**，现场表现是：
  「**物理链路通、有载波、但没 IP**」，而且 **APP 里改 IP 也不生效**（改的是不存在的档案）。
  只看 ping 很容易误判，极难查。

------------------------------------------------------------------------
14.1 脚本做了什么
------------------------------------------------------------------------
- 按 701 现场已验证的档案值建 `<ifname>-static`：地址 192.168.123.55/24, 192.168.144.87/24、
  网关 192.168.123.1、connection.autoconnect-priority -999、802-3-ethernet.auto-negotiate no、
  ipv4.route-metric -1、ipv6.method auto
- 自动探测图传网口（**有载波 + 当前无 IPv4 + 名字形如 ethN**），并按 USB VID:PID 排除已知非图传口
  （雷达 USB-LAN 0fe6:9900、4G 模块 2c7c:0125）；**候选不唯一时不猜**（避免把 144 地址配到雷达口上）
- **无条件补齐 eth1-static + eth2-static 两份**，兜底机型命名差异（档案绑到不存在的网卡时
  NM 不会激活它，无害 —— 701 现场就是这么存的）
- 边界：只新增/校正它自己的 `<ifname>-static` 档案；不动 WiFi/热点/4G、不删地址、不 flush 路由、
  不重启网络。单步失败只 warn，不中断装机。

------------------------------------------------------------------------
14.2 手工等价操作（现场补跑 / 自动探测不准时）
------------------------------------------------------------------------
  curl -fsSL -o /tmp/install_static_ips.sh \
    https://gitee.com/electech6/d360_deploy/raw/master/net/install_static_ips.sh
  sudo bash /tmp/install_static_ips.sh --dry-run     # 只打印计划与将执行的 nmcli，不改任何档案
  sudo bash /tmp/install_static_ips.sh               # 正式配（幂等：已存在则校正为规范值）

探测不准时（候选多于一个 / 一个都没探测到）就明确指定或排除：
  sudo bash /tmp/install_static_ips.sh --ifname eth2
  sudo bash /tmp/install_static_ips.sh --exclude eth0
可用参数：--ifname <网口> / --exclude <网口[,网口]> / --peer <对端IP>（默认 192.168.144.11，
只用于 ip neigh 的验收判断）/ --no-up（只建/校正档案，不激活）/ --dry-run。

------------------------------------------------------------------------
14.3 验收（现场凭这三条判断链路真通）
------------------------------------------------------------------------
  ip -4 -br addr show <图传网口>    # 应有 192.168.144.87/24（与 192.168.123.55/24）
  ip route | grep 144               # 应有 192.168.144.0/24 dev <图传网口>
  ip neigh | grep 192.168.144       # 出现 **REACHABLE** = 对端在线、链路真通
                                    # 这一条比 ping 自己可靠；邻居表里还没条目时先触发一次流量：
                                    # ping -c 2 -I <图传网口> 192.168.144.11 && ip neigh | grep 192.168.144

**优先级别搞反**：实测 **WiFi 600 < 4G 20102 < 图传 20103** —— 图传 metric 最大、**不抢上网**。
  若发现图传口成了 metric 最小的默认路由，那是**网口插错了**，先查线；
  不要在设备上改路由去绕。

⚠ 状态标注：`net/install_static_ips.sh` 到目前**只在 stub 下跑过 --dry-run，未在真机完整跑过**。
  现场跑完以 `ip neigh | grep 192.168.144` 出 `REACHABLE` 为判据（出不来 → 先查图传模块供电与网线）。

十五、4G / CAT4 上网（客户自理；我方只做识别与验证）
====================================================================

- **SIM 与流量套餐由客户自行开通** —— 我方**不代办**激活/实名/续费/查余量。
- **天线必须接好**：换 BOX、拆装外壳时最容易漏接 4G 天线；`signal quality: 0%` 的最常见原因就是天线没接。
- 客户自助激活文档：Gitee `d360_deploy` → `net/CUSTOMER-4G-ACTIVATION.md`（下面只是三条判据的速查）。

------------------------------------------------------------------------
15.1 三条判据
------------------------------------------------------------------------
① 模块 / SIM 识别：
     systemctl is-active ModemManager && mmcli -L && mmcli -m 0
   看 `mmcli -m 0` 的 SIM 段：有 `primary sim path: ...` = **识别到**；
   `failed reason: sim-missing` = **没识别到**（没插好 / 卡座接触不良 / 卡未激活）。
   再看状态段：`state: registered` + 信号正常 = 已注册上基站；
   `state: searching` + `signal quality: 0%` = 多半是**天线没接**。

② 数据口有没有地址：
     ip -br addr show <4G 接口>

③ 验证能不能出去 —— **用 curl 显式绑定接口**，不要动路由：
     curl --interface <4G 接口> -sS -m 10 -o /dev/null -w '%{http_code}\n' https://www.xfyun.cn/
   读法：`200/301/302` = 这条通道能上网；`000` + `Could not resolve host` = DNS 问题
   （`--interface` 只绑出口网卡，DNS 仍走系统解析器），**不是通道不通**；`000` + 超时 = 这条通道不通
   （查套餐 / APN / 信号）。

⚠ **绝对不要用「关掉 WiFi」来测 4G**：运维是经 WiFi SSH 上来的，一关就断连；万一 4G 其实不通，
  设备就**彻底失联**了（只能到现场，或靠 FRP 救）。

------------------------------------------------------------------------
15.2 ⚠ 一条未确证的事（不要凭它施工）
------------------------------------------------------------------------
D360 的 4G **到底走 PPP `ppp0` 还是 ECM `usb1`，目前尚无定论**：
- 工作区事实源 `facts/jetson_profile.yaml` 的 cat4 块（**CONFIRMED 2026-09-01，真机验证**）记录走
  **PPP `ppp0`**：metric 20900、NM 连接名 `China-Mobile-4G`、APN `cmnet`，并明确写
  「**禁止硬编码 usb1 或套用 EC800K 的 ECM 流程**」。
- 现场看到的 `usb1` / `192.168.225.x/24`（metric ~20102）更像 **BOX（EG25 / EC800K，RNDIS/ECM）**
  的通路，不是 D360 上这颗 EC20F 的表现。
→ **交付设备上不要做 `AT+QCFG="usbnet"` 这类改模式的实验**：那是写进模块 NVRAM 的操作，
  可能把**已经确证可用的 ppp0 通路弄坏**；要做只在实验室设备、并且有现场控制台（HDMI 或串口）兜底时做。
→ 细节见 `net/CUSTOMER-4G-ACTIVATION.md` 第 5 节（该节整体标 **NEEDS_CONFIRMATION**）。

十六、交付前清理（交给客户之前必须逐项走完）
====================================================================
完整清单（含每步命令与验收）见 Gitee `d360_deploy` → `docs/DELIVERY-CLEANUP-CHECKLIST.md`。
下面是现场实战后必须记住的 6 条要点：

1. **讯飞凭据换成空模板，不是删文件**
   `/home/jetson/xf_chat_standalone/xf_config.yaml` 在 compose 里是**单文件 bind mount**；源文件
   不存在时 Docker 会**建一个同名目录** → 容器内该是文件的位置变成目录 → 语音容器启动失败。
   所以只把值清空（键保留、值为 ""），文件必须始终**存在且是普通文件**、`0600 jetson:jetson`。

2. **值级扫描验证（别只靠肉眼）**
   `voice/tools/scan_credential_values.py` 的**第一个参数必须是模式文件**（每行一个真实凭据值，0600）：
     sudo python3 scan_credential_values.py <模式文件> /home/jetson /etc/slamibot /var/lib/slamibot
   期望输出 `NO_CREDENTIAL_VALUES_OK`。
   ⚠ **不用 root 跑会对读不到的文件静默跳过 → 得到「假 OK」**（必须 sudo）。
   ⚠ **模式文件本身就是凭据，用完必须删**（`sudo shred -u` 或 `rm -f`），删完再扫一遍确认它没被留下。

3. **导航测试残留：先停容器再删，再启动**
   `/var/lib/slamibot/scout-nav/{maps,fastlio,db}` —— 我方建的地图、FAST-LIO 建图产物、
   `db/captures/*.jpg`（现场照片）与 `db/tts_cache`（播报缓存）属客户数据，不能留。顺序不能反：
     sudo docker stop scout-nav
     sudo rm -rf /var/lib/slamibot/scout-nav/maps \
                 /var/lib/slamibot/scout-nav/fastlio \
                 /var/lib/slamibot/scout-nav/db
     sudo docker start scout-nav          # 容器会重建空目录与一份干净数据库
   验收：`find /var/lib/slamibot/scout-nav -name '*.jpg'` 无输出、`/api/map/list` 为空、
   `/health` 仍 `rosbridgeConnected:true`。
   （1.2.2 起镜像不带演示地图，**清完之后地图列表为空是正常的**，不是故障。）

4. **我方 SSH 公钥全部清空 —— 但删之前必须先确认密码登录还开着**
   顺序错了会**永久锁死设备**（只能现场接 HDMI/串口救）：
     sudo grep -rniE '^\s*PasswordAuthentication' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
   **没有该行 = 用默认值 yes = 密码登录可用**，这时才可以清空 `~/.ssh/authorized_keys`
   （jetson 与 root 都看）。出现 `PasswordAuthentication no` → **先不要删**，让客户决定，
   或保留一把客户自己的钥匙。
   清完**新开一个会话**验证能登录 —— 当前会话先别关。

5. **删完公钥就只剩密码登录了** → 出厂默认弱口令等于裸奔。
   强口令**必须由客户设置或按客户的账号策略设置，我方不得代设、不得代记**；
   交付确认单上写明「首次上电后设置强口令」，并当面提醒客户。

6. **临时配过的免密 sudo 必须删掉**
   `sudo ls -la /etc/sudoers.d/` 找出我方那份（看清内容再删）→ `sudo rm /etc/sudoers.d/<file>`
   → `sudo visudo -cf /etc/sudoers` 校验，然后验证已恢复要密码：
     sudo -k; sudo -n true; echo $?     # 非 0 = 需要密码，符合预期
     sudo -l | grep -i nopasswd         # 应无输出
   **不要**用编辑器直接改 /etc/sudoers（改坏就彻底锁死）。

最后一步永远是**新开会话复验**：从全新会话能登录、并再扫一遍仍 `NO_CREDENTIAL_VALUES_OK`，
才算清理真正生效。
