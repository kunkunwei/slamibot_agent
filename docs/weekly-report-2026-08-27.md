## 一、本阶段工作概览

本阶段主要围绕 **运行环境稳定性、APP 功能补充、导航问题排查、音视频链路优化和现场售后支持** 展开。已完成容器与镜像重构、ROS 时间统一、容器重启后的节点/话题恢复机制、APP 点位拍照及定位功能、TTS 通道验证、导航页视频流后端接入等工作；当前主要遗留问题集中在 **导航稳定性与轨迹质量、相机 USB/温度稳定性、视频带宽占用以及 AMCL 定位效果**。

## 二、已完成工作

### 1. 导航镜像与容器环境重构

- 重新编译并构建导航镜像，创建 `scout-nav` 容器。
- 排查发现旧容器的 ROS 运行环境存在污染，执行 `rosrun` 模糊查找时会匹配到多个 `nav_multi_node.py`，造成实际运行脚本不唯一。
- 通过重新构建镜像和容器，恢复了脚本及 ROS 运行环境的一致性。
- 修改 Dockerfile，重新梳理镜像构建规则和容器依赖，去除不必要的 `source` 依赖，降低容器启动对交互式 Shell 环境的依赖。

### 2. 容器重启后的 ROS 节点与话题恢复

- 针对 APP 前后端在容器删除、停止或重启后容易连接失败的问题进行了排查。
- 已确认问题与 **容器非优雅退出、ROS Master 中节点注册状态未及时清理、节点和话题恢复顺序不完整** 有关，表现为：
  - 节点名称仍显示存在，但实际话题没有数据；
  - rosbridge 或 APP 无法正常获取地图、点云及导航状态；
  - 新容器启动后，同名节点和旧注册信息发生冲突或恢复异常。
- 制定了固定的容器停止、清理、启动和验证流程。
- 增加容器重启后的节点、话题检查与恢复脚本，并完成测试，可解决部分残留节点注册及话题未恢复问题。

> 技术说明：目前能够确认的是“退出不完整和注册/恢复异常”。孤儿进程、TCP 端口释放延迟等属于可能机制，仍需结合进程、Master XML-RPC 和网络日志进一步确认，不作为唯一根因下结论。

### 3. APP 功能补充与遥控性能优化

- APP 增加点位拍照功能，并完成前后端交互和拍照测试。
- 增加 TTS 语音播报功能；与 BOX 联调 `espeak-ng`，确认语音输出通道正常。
- 后续计划将当前方案转换为团队提供的语音识别包。
- 优化 APP 遥控链路延迟：
  - 增加点云展示开关；
  - 支持手动关闭点云订阅；
  - 降低图传网络下点云数据对带宽和遥控指令的影响。
- APP 3D 点云界面中代表机器人的三角箭头已可跟随机器人移动。
- 补充实现手动定位和重定位相关功能。

### 4. 导航页视频流与拍照链路

- 已补充 APP 导航控制页面的视频流后端接口。
- 当前视频链路为：ROS 压缩图像话题 → FastAPI 最新帧缓存 → HTTP MJPEG → APP。
- 已验证导航页面实时视频和拍照功能可用。
- 测试发现 MJPEG 带宽占用较高，开启视频后会影响遥控手感，后续需要降低帧率、分辨率或压缩质量。

### 5. ROS 时间统一问题修复

- 排查导航无法启动的问题，发现 `nav_multi` 可能在 `/use_sim_time` 和 `/clock` 就绪前完成 `rospy.init_node()`，导致其未进入正确的 ROS 仿真时间体系。
- 已修复导航 ROS 时间统一问题。
- 明确了推荐启动顺序：

```text
等待 ROS Master
→ 设置 /use_sim_time=true
→ 等待 /clock 首帧
→ 启动 nav_multi
→ 确认 nav_multi 已进入 ROS 时间体系
→ 注册并开放导航 Service
```

- 规划在手动模式切换至导航模式前增加后端预检，检查：
  - `/use_sim_time == true`；
  - `/clock` 存在 Publisher 且持续有新消息；
  - `/nav_multi` 唯一运行；
  - `/nav_multi` 已订阅 `/clock`；
  - `nav_multi` ROS 时间与 `/clock` 位于同一时间域。
- 只有预检全部通过后，才启动 `map_server`、`amcl`、`move_base` 和 `pcd_map_publisher`；否则拒绝进入导航并返回明确错误。

### 6. 导航 TF 与定位链路排查

- 重新部署 2D 导航后发现 TF 树缺少 `laser → base_link` 变换。
- 该问题会导致 `pointcloud_to_laserscan` 无法完成坐标变换，进而造成 `/scan` 停止发布、AMCL 无法定位、costmap 无法获得障碍物信息。
- 已通过与 Gitee 仓库版本对比补充缺失配置。
- 导航曾成功运行，确认其中一个关键问题是：**初始位姿不准确 → 规划起点错误 → 全局规划失败**。
- APP 初始位姿设置的坐标映射精度仍需优化；当前 WEB 端设置效果相对更准确。

### 7. 重定位方案排查与回退

- 排查发现机器人静止时 `/amcl_pose` 更新不连续，容易使 APP 上的位姿显示和重定位结果看起来没有及时变化。
- WEB 端原重定位按钮调用 AMCL `/global_localization`，其本质是全图随机撒粒子；在办公室环境下定位和校正效果较差。
- 对比仓库原始代码后发现，效果较好的版本使用 3D 地图定位；但当前 `FAST_LIO_LOCALIZATION` 未编译出可用二进制，现有安装产物主要是建图模式，暂时无法直接启用 3D 地图定位。
- 经多轮排查后恢复为 2D 重定位方案。
- 将容器回滚至三天前版本并修复时间同步后，重定位恢复正常。

### 8. 六麦阵列与语音交互问题修复

- 测试六麦阵列的在线大模型语音交互独立模式。
- Jetson 重启后出现声卡设备漂移，程序错误连接到 `NVIDIA Jetson Orin NX APE`，导致无法识别麦克风输入。
- 排查入口脚本后发现存在强制绑定：

```bash
export AUDIO_MIC_DEVICE=plughw:3,0
```

- 修改音频设备绑定逻辑后，声卡选择问题已修复。

### 9. 现场售后问题处理

| 轮次 | 问题现象 | 排查结果 | 处理结果 |
|---|---|---|---|
| 第一轮 | APP/ROS 功能异常、节点或话题不可用 | ROS 节点注册残留或容器重启后恢复不完整 | 暂停容器、清理节点并重新启动，功能恢复 |
| 第二轮 | 雷达不发布消息 | `eth0`、`eth1` 配置了相同 IP，产生网络冲突 | 修改 IP 并持久化，雷达通信恢复 |
| 第三轮 | 相机 USB 频繁断连 | MAX 功耗模式无明显改善；三路 20 FPS 时负载较高 | 将出图帧率降至 5 FPS 后可稳定出图；USB 线路、供电或总线负载仍需进一步确认 |

## 三、测试与当前状态

### 已通过或基本可用

- 新镜像及 `scout-nav` 容器可运行；
- APP 前后端基本交互；
- 点位拍照；
- TTS 语音输出通道；
- ROS 时间统一修复；
- 容器重启后的节点/话题检查与部分恢复；
- APP 点云开关及遥控带宽优化；
- APP 3D 视图机器人位姿跟随；
- 手动定位、重定位功能补充；
- 导航页面视频流及拍照；
- 六麦阵列错误声卡绑定问题修复。

### 仍不稳定或效果较差

1. **导航稳定性**：仍可能出现地图话题不发布、全局 costmap 无新消息、全局规划失败等问题。
2. **导航控制效果**：机器人运动存在滞后和超调，轨迹弯曲的实际原因尚未完成定位。
3. **定位效果**：办公室环境下 AMCL 的全局重定位和校正效果较差，APP 初始位姿坐标映射仍需优化。
4. **相机稳定性**：高帧率、多路视频时容易过热或 USB 掉驱动，目前降低到 5 FPS 后较稳定。
5. **视频带宽**：MJPEG 占用带宽较大，会影响遥控链路实时性。
6. **远程观测条件**：通过 MobaXterm SSH 打开 RViz 时画面卡顿，难以实时观察 TEB 和全局路径；投屏软件版本受限，现场观测手段需要改善。

## 四、关键问题总结

| 问题方向 | 当前结论 | 状态 |
|---|---|---|
| ROS 环境污染 | 同名脚本多份、运行入口不唯一 | 已通过重建镜像处理 |
| 容器重启后“假死” | ROS 注册残留、退出及恢复顺序不规范 | 已增加流程和恢复脚本，仍需继续增强 |
| ROS 时间域不一致 | `nav_multi` 启动早于 `/use_sim_time`、`/clock` 就绪 | 已修复，预检机制待完善 |
| `/scan` 中断 | 缺失 `laser → base_link` TF | 已补充配置 |
| 全局规划失败 | 初始位姿不准、costmap 无新消息等多因素 | 部分定位，仍在排查 |

## 五、下一步计划

1. **固化容器生命周期**：完善优雅退出、节点注销、启动顺序、健康检查和失败恢复流程。
2. **完善导航模式预检**：在开放导航前自动检查 ROS Master、时间域、`/clock`、节点唯一性、TF、`/scan`、地图和 costmap。
3. **继续定位导航轨迹问题**：重点检查初始位姿、里程计、TF 延迟、TEB 参数、局部/全局 costmap 更新频率及路径跟踪误差。
4. **优化 APP 初始位姿映射**：对齐 APP 与 WEB 的坐标换算、地图缩放、旋转和原点处理。
5. **优化视频链路**：优先将导航预览降低到约 3～4 FPS，再评估分辨率、JPEG 质量或 H.264/WebRTC 等低码率方案。
6. **验证相机硬件稳定性**：分别测试单路/多路相机、不同帧率、USB 端口、线材、供电和温度，明确是软件负载还是硬件链路问题。
7. **推进语音方案切换**：将已验证的 TTS/音频通道接入团队提供的语音识别包，并验证 Jetson 重启后的设备稳定绑定。
8. **改善现场观测方式**：更换可用投屏方案或准备便携显示器，保证 RViz、TEB 和全局路径可以实时观测。

## 六、周会口头汇报稿（约 3 分钟）

这几天的工作主要集中在五个方面：容器环境、APP 功能、导航排障、音视频链路和现场售后。

第一，重新构建了导航镜像和 `scout-nav` 容器。旧容器存在 ROS 环境污染，同一个 `nav_multi_node.py` 能搜索到多份，重新构建后已经解决。同时重构了 Dockerfile 和依赖规则，降低启动过程对 `source` 环境的依赖。

第二，重点处理了容器重启后节点和话题容易失效的问题。目前确认与非优雅退出、ROS Master 注册残留和恢复顺序不完整有关。已经制定固定重启流程，并增加节点、话题检查和恢复脚本，能够解决一部分地图、点云和 rosbridge 不恢复的问题。后续还会把时间、TF、scan、地图和 costmap 检查统一放到导航启动预检里。

第三，APP 侧补充了点位拍照、TTS、手动定位、重定位、3D 视图机器人位姿跟随和导航视频流。点云订阅现在可以手动关闭，能够明显降低图传网络下的带宽占用和遥控延迟。视频和拍照已经可用，但 MJPEG 带宽较高，后续准备先把预览帧率降到 3 到 4 帧。

第四，导航方面修复了 ROS 时间不统一，以及 `laser` 到 `base_link` 的 TF 缺失问题。导航已经成功跑通过一次，也确认初始位姿不准会直接导致规划起点错误和全局规划失败。目前剩余问题主要是 AMCL 定位效果一般、APP 初始位姿映射不够准，以及运动存在滞后、超调和轨迹弯曲，还需要继续结合 RViz 和 costmap 数据排查。

第五，售后处理了三类问题：ROS 节点残留、网口 IP 冲突导致雷达无数据、以及多路相机高帧率下 USB 掉线。相机降低到 5 FPS 后暂时稳定，但还需要进一步确认线材、供电、USB 总线负载和温度因素。六麦阵列方面也定位到入口脚本强制绑定了错误声卡，修改后已经恢复。

下阶段重点是固化容器生命周期和导航启动预检，继续解决定位与轨迹质量问题，并优化视频带宽和相机稳定性。
